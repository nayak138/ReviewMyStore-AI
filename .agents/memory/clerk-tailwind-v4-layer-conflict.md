---
name: Clerk cssLayerName + manual @layer statement can break unrelated layout
description: A pre-declared `@layer theme, base, clerk, components, utilities;` statement (as suggested for Clerk+Tailwind v4 dark-mode contrast) can silently corrupt positioning of unrelated elements elsewhere in the app.
---

In this project (ReviewMyStore.ai), adding `@layer theme, base, clerk, components, utilities;` before `@import 'tailwindcss'` (paired with `cssLayerName: "clerk"` in Clerk's `appearance` config) fixed Clerk's dark-mode text-contrast bug, but broke an unrelated desktop sidebar: a `position: relative` flex child with `inset-y-0 left-0` ended up rendering at `x = -width` (shifted fully off-screen to the left) even though every computed offset (`left/right/top/bottom`) read `0px` and `transform` read `none`. This is not explainable by the CSS spec for relative positioning taken at face value — it reproduced consistently with the `@layer` statement present and disappeared consistently when it was removed, isolated via bisection (toggle the one line, restart, re-screenshot).

**Why:** Tailwind v4's own `@import 'tailwindcss'` internally emits a second, competing `@layer theme, base, components, utilities;` declaration (visible by curling the dev server's compiled CSS module). Layering two `@layer` name-list statements that both mention overlapping layers is spec-legal, but combined with Lightning CSS's handling of *logical* inset properties (Tailwind v4 compiles `inset-y-0` to `inset-block: 0px`, not physical `top`/`bottom`) it produced a real, reproducible layout corruption in this project. Root cause was not fully isolated beyond "the manual pre-declared `@layer` list is the trigger" — treat it as a known-bad interaction, not a fully explained one.

**How to apply:** For Clerk (or any vendor) dark-mode/contrast fixes on this stack (Tailwind v4 + Vite), do NOT reach for a manual `@layer theme, base, clerk, components, utilities;` pre-declaration + `cssLayerName`. Instead, add `!` (important) Tailwind modifiers directly to the specific text/background classes in the vendor's `appearance.elements` map (e.g. `headerTitle: "!text-zinc-950 dark:!text-zinc-50"`). `!important` wins regardless of cascade-layer order, sidesteps the whole layer-ordering interaction, and is easy to verify with a targeted contrast screenshot. Always re-check unrelated fixed/relative-positioned layout (sidebars, drawers) after any global `@layer` edit in this stack — bisect by toggling the line and restarting if something goes visually blank.
